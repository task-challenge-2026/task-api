# Decisions log: HMCTS caseworker task manager

Running log of design decisions and reasons. Feeds the README's "Decisions and trade-offs" section and interview prep.

## Scope

| Area      | Brief requires                                           | Decision                                                        |
| --------- | -------------------------------------------------------- | --------------------------------------------------------------- |
| Create    | title, description (optional), status, due date/time     | `POST /api/v1/tasks`                                            |
| Read      | one task by ID, all tasks                                | `GET /api/v1/tasks/:id`, `GET /api/v1/tasks` (list, not search) |
| Update    | status only                                              | `PATCH /api/v1/tasks/:id/status`                                |
| Delete    | one task                                                 | `DELETE /api/v1/tasks/:id`                                      |
| Frontend  | full CRUD, user-friendly                                 | GOV.UK Design System via HMCTS frontend starter                 |
| Technical | tests, database, validation and errors, API docs, README | All in scope                                                    |

## Decisions

### 1. No users or authentication

- **Decision:** Not built. The brief has no users or permissions.
- **Why:** Out of scope; adding it is over-engineering for a technical test.
- **Next step (README):** In production, tasks would be scoped to the authenticated caseworker via HMCTS identity and access management.

### 2. Statuses

- **Decision:** `TODO`, `IN_PROGRESS`, `ON_HOLD`, `DONE`.
- **Why:** Small, defensible set. `ON_HOLD` reflects real casework, where tasks stall waiting on parties, evidence or the judiciary.

### 3. Overdue is derived, not stored

- **Decision:** API returns `isOverdue` = `dueAt < now` AND `status != DONE`. UI shows a red GOV.UK tag.
- **Why:** A stored flag goes stale as time passes. Deriving it keeps data consistent with no background jobs.

### 4. Due date cannot be in the past on create

- **Decision:** `POST /api/v1/tasks` rejects a past `dueAt` with 422 (`DATE_IN_PAST`) and a clear message.
- **Why:** Prevents data entry errors on new work.
- **Allowed:** Status updates on overdue tasks, so they can be progressed and closed.
- **Next step (README):** Historic or backdated tasks would be loaded through an admin-only bulk import with audit logging, not the standard create endpoint.

### 5. Time zones

- **Decision:** Store `dueAt` in UTC. Display in Europe/London.
- **Why:** Avoids tasks shifting by an hour across clock changes.

### 6. Sorting and filtering on the list endpoint

- **Decision:** User-controlled sorting and an optional status filter.
  - `?sort=dueAt|status|createdAt` (default `dueAt`)
  - `?order=asc|desc` (default `asc`)
  - `?status=TODO|IN_PROGRESS|ON_HOLD|DONE` (optional)
- **Why:** Due date matters most, but caseworkers also navigate by status and by when work arrived.
- **Detail:** Status sorts by workflow order (TODO, IN_PROGRESS, ON_HOLD, DONE), not alphabetically.
- **Detail:** Sort and filter values are validated against an allowlist; anything else returns 422. Prevents injection via sort fields and gives clear errors.
- **Next step (README):** Pagination for large caseloads.

### 7. Stack

- **Decision:** Node.js + TypeScript, Express 5, Postgres (Docker Compose), Knex for migrations and queries, Jest + Supertest, Zod for validation, OpenAPI for docs. Frontend: HMCTS frontend starter with the GOV.UK Design System.
- **Why:** Node.js and Postgres are on HMCTS's core stack; TypeScript adds type safety; GOV.UK Design System matches how HMCTS builds public services.
- **Detail:** `createApp()` is separate from `server.ts` so tests run against the app without opening a network port.

### 8. Task IDs are UUIDs

- **Decision:** `id` is a UUID generated by Postgres (`gen_random_uuid()`).
- **Why:** Sequential numbers are guessable (`/tasks/1`, `/tasks/2`) and reveal task volumes. UUIDs prevent ID enumeration, which matters for a justice system even before authentication is added, and stay unique across systems for future imports.
- **Trade-off:** Less readable than numbers. Ordering is handled by `createdAt` instead.

### 9. Database schema and migrations

- **Decision:** Schema managed through Knex migrations, with an `up` and a `down` for every change.
- **Why:** Versioned, repeatable and reversible changes instead of manual SQL. Knex also builds parameterised queries, which protects against SQL injection.
- **Schema details:**
  - `title` limited to 200 characters and required; `description` optional (stored as an empty string when not provided, see decision 14).
  - `status` restricted by a database check constraint to `TODO`, `IN_PROGRESS`, `ON_HOLD`, `DONE`, so invalid values are rejected even if they bypass the API.
  - `due_at`, `created_at` and `updated_at` stored as timestamps with time zone (UTC).
  - Indexes on `due_at` and `status`, because the list endpoint sorts and filters on them.
- **Trade-off:** A check constraint rather than a Postgres enum type, because it is simpler to change if statuses are added later.

### 10. Error response format (API)

- **Decision:** All errors return `{ error: { code, message, details? } }`. Field errors return `details` with one entry per field: `{ field, code, message }`.
- **Audience:** API messages are for developers. The frontend maps codes to user-facing text (see decision 11).

| Status | Code                | When                                                               |
| ------ | ------------------- | ------------------------------------------------------------------ |
| 400    | `MALFORMED_JSON`    | Request body is not valid JSON                                     |
| 404    | `NOT_FOUND`         | No task with that ID, including IDs that are not valid UUIDs       |
| 404    | `ROUTE_NOT_FOUND`   | URL or method does not exist                                       |
| 413    | `PAYLOAD_TOO_LARGE` | Body exceeds size limit                                            |
| 422    | `VALIDATION_ERROR`  | Well-formed request with invalid values (includes `details`)       |
| 500    | `INTERNAL_ERROR`    | Unexpected error; generic message, details logged server-side only |

- **Field codes:** `REQUIRED`, `TOO_LONG`, `INVALID_FORMAT`, `INVALID_VALUE`, `DATE_IN_PAST`, `UNKNOWN_FIELD`.
- **Why 422:** Separates "the request is broken" (400) from "the request is valid JSON but breaks the rules" (422).
- **Why 404 for invalid IDs:** A malformed ID can never match a task, so the answer is the same as any missing task. Reveals nothing about ID format and keeps clients simple. Invalid UUIDs are caught before querying so they never cause a database error.
- **Why reject unknown fields:** Catches client typos instead of silently ignoring them, and keeps `PATCH` limited to `status`.
- **Delete of a missing task:** 404, consistent with other endpoints.
- **Status on create:** Required. The database default (`TODO`) remains as a safety net only.
- **One error per field:** If a field fails several rules, only the first is returned, so users never see duplicate messages for one input.
- **Missing vs invalid:** A field that was not sent returns `REQUIRED`; a field that was sent but is wrong returns the specific code.
- **Alternative considered:** RFC 9457 Problem Details. A recognised standard, but heavier than needed for this scope.

### 11. User-facing error messages (frontend)

- **Decision:** The frontend never shows API messages directly. It maps error codes to plain-English text following the GOV.UK Design System error message guidance, shown in an error summary at the top of the page and next to each field.

| Field / code                       | User sees                                                    |
| ---------------------------------- | ------------------------------------------------------------ |
| title / `REQUIRED`                 | Enter a title                                                |
| title / `TOO_LONG`                 | Title must be 200 characters or fewer                        |
| status / `REQUIRED`                | Select a status                                              |
| status / `INVALID_VALUE`           | Select a status from the list                                |
| dueAt / `REQUIRED`                 | Enter a due date                                             |
| dueAt / `INVALID_FORMAT`           | Due date must be a real date                                 |
| dueAt / `DATE_IN_PAST`             | Due date must be in the future                               |
| `NOT_FOUND` (page)                 | Task not found. It may have been deleted.                    |
| `INTERNAL_ERROR` / network failure | Sorry, there is a problem with the service. Try again later. |

- **Why:** Developer messages and user messages have different audiences. Mapping by code keeps wording consistent, lets content change without touching the API, and follows GOV.UK standards caseworkers already know.
- **Not shown to users:** `MALFORMED_JSON`, `ROUTE_NOT_FOUND`, `PAYLOAD_TOO_LARGE`, `UNKNOWN_FIELD`. These indicate a frontend bug; the user sees the generic service error and the detail is logged.

### 12. Description length

- **Decision:** `description` is optional and capped at 2000 characters.
- **Why:** Prevents oversized payloads in a free-text field while leaving room for real case notes.

### 13. Validation rules not covered above

- **Trimming:** Title and description are trimmed before validation, so a whitespace-only title returns `REQUIRED`.
- **Time zone required on `dueAt`:** Must include `Z` or an offset (e.g. `+01:00`). Local times without a zone are rejected as `INVALID_FORMAT` so the API never guesses. The frontend builds the full value from the GOV.UK date input.
- **Status column:** `varchar(20)`, enough for current and plausible future status names.
- **Migration status list:** The migration keeps its own copy of the statuses on purpose. Migrations are frozen snapshots and must not change if the app's list changes.

### 14. No description is stored as an empty string

- **Decision:** `description` is `NOT NULL DEFAULT ''`. Omitting it stores `''`. Sending `null` is rejected (`INVALID_FORMAT`).
- **Why:** One representation of "no description" instead of two (`NULL` and `''`). GOV.UK forms already submit empty fields as `''`.
- **Display:** The frontend shows "No description" when it is empty; that text is never stored.
- **Change made via a new migration**, not by editing the original, because applied migrations must never be rewritten.

### 15. `updated_at` maintained by a database trigger

- **Decision:** A `BEFORE UPDATE` trigger sets `updated_at = now()` on every update.
- **Why:** Guaranteed for every update path, including future endpoints and manual SQL, so it can never be forgotten in application code.
- **Trade-off:** Logic lives in the database rather than the app; documented here so it is not hidden.

### 16. Separate test database

- **Decision:** Tests run against a `tasks_test` database, configured in `.env.test` and loaded by a Jest setup file using Node's built-in `util.parseEnv`, written directly into Jest's `process.env` (`process.loadEnvFile` did not reach Jest's sandboxed environment).
- **Why:** Tests never touch dev data and can safely empty tables between runs.
- **Detail:** `.env.test` is committed because it only contains the throwaway local Docker credentials already in `docker-compose.yml`. `.env` stays ignored.
- **Tests run serially (`--runInBand`):** Several test files share and truncate the same tables, so running them in parallel would cause flaky failures.

### 17. API field naming

- **Decision:** API requests and responses use camelCase (`dueAt`, `createdAt`, `isOverdue`). The database uses snake_case (`due_at`). The repository converts between them in one function (`toTask`).
- **Why:** Consistent naming for API consumers, standard for JavaScript APIs, and database naming stays independent of the API contract.
- **Dates:** Returned as ISO 8601 strings in UTC (e.g. `2026-11-10T09:00:00.000Z`).

### 18. API base path and versioning

- **Decision:** Task endpoints live under `/api/v1/tasks`. `/health` stays unversioned at the root.
- **Why:** The brief does not specify URLs. Versioning lets a future `/v2` run alongside `/v1`, so the frontend and other clients are not broken by changes. `/api` separates the API from any pages served on the same host.
- **Health check:** Unversioned because it is used by infrastructure (load balancers, monitoring), not API clients, and must not move between versions.
- **Endpoints:**
  - `POST /api/v1/tasks`: create
  - `GET /api/v1/tasks`: list (sort, order, status filter)
  - `GET /api/v1/tasks/:id`: get one
  - `PATCH /api/v1/tasks/:id/status`: update status
  - `DELETE /api/v1/tasks/:id`: delete
  - `GET /api/v1/tasks/:id/history`: status audit trail

### 19. Response header hardening

- **Decision:** The `X-Powered-By: Express` header is disabled.
- **Why:** Revealing the framework helps attackers target known vulnerabilities. Removing it costs nothing.
- **Next step (README):** In production, add `helmet` for a full set of security headers (content security policy, HSTS and others).

### 20. List endpoint (`GET /api/v1/tasks`)

- **Response:** Wrapped as `{ "tasks": [...] }`, so pagination fields (e.g. `total`) can be added later without breaking clients.
- **Query parameters:** `sort` (`dueAt` default, `status`, `createdAt`), `order` (`asc` default, `desc`), optional `status` filter. Validated with Zod; invalid values return 422 `INVALID_VALUE`.
- **Unknown query parameters:** Rejected with `UNKNOWN_FIELD`, consistent with the request body rule (decision 10).
- **Status sort:** Workflow order (TODO, IN_PROGRESS, ON_HOLD, DONE) using `array_position`, not alphabetical.
- **Tie-breaking:** Always followed by `due_at` ascending, then `id`, so the order is deterministic and never changes between requests.
- **Safety:** Sort columns come from a fixed mapping, never from user input. The status list is passed as query parameters.

### 21. Update and delete responses

- **PATCH `/api/v1/tasks/:id/status`:** Returns 200 with the full updated task, so the frontend can show the new status and `updatedAt` without a second request. Accepts `status` only.
- **DELETE `/api/v1/tasks/:id`:** Returns 204 No Content with an empty body.
- **Single query, no read first:** Update and delete each run one query and use the affected row count to detect a missing task. Faster, and avoids a race where the task changes between a check and the write.
- **Order of checks:** Invalid ID returns 404 before the body is validated, so the response for a bad ID is always the same.

### 22. API documentation

- **Decision:** Hand-written OpenAPI 3 spec in `docs/openapi.yaml`, served as interactive Swagger UI at `/api-docs` and raw JSON at `/api-docs/openapi.json`.
- **Why hand-written:** Readable and reviewable as a document, with validation rules described in plain language.
- **Drift protection:** A test compares the routes registered in Express with the paths in the spec, in both directions, so an undocumented or stale endpoint fails CI.
- **Alternative considered:** Generating the spec from the Zod schemas. Guarantees accuracy of field rules but adds a library and setup; the drift test covers the main risk at lower cost.

### 23. Continuous integration

- **Decision:** GitHub Actions runs on every push to `main` and every pull request: formatting check, lint, type check, test migrations, then the full test suite against a real Postgres 16 service.
- **Why:** Proves the project works on a clean machine, not just mine, and stops broken code reaching `main` unnoticed.
- **Detail:** Cheapest checks run first so failures are fast. `npm ci` installs exact locked versions. A health check waits for Postgres before migrating.

### 24. Status audit trail

- **Decision:** Every status change is recorded in a `task_status_history` table: task, previous status, new status, and when it changed. This includes the initial status on creation and a final entry when a task is deleted.
- **Why:** Casework must be auditable. Overwriting a status loses the record of what happened and when.
- **How:** A database trigger (`AFTER INSERT OR UPDATE OF status OR DELETE`) writes the history, the same approach as decision 15. It cannot be bypassed or forgotten by any endpoint, current or future, or by manual SQL.
- **Nothing is wiped:** History has no foreign key to `tasks`, so it is retained after a task is deleted, with a final entry recording the deletion. The API only exposes history for tasks that still exist.
- **No-op updates:** Setting a task to the status it already has does not create an entry.
- **Endpoint:** `GET /api/v1/tasks/:id/history`, oldest first, wrapped as `{ "history": [...] }`.
- **Next step (README):** Record who made each change once authentication exists, and an optional reason for the change (e.g. "On hold: awaiting evidence").

### 25. Task deletion permissions (next step)

- **Next step (README):** Deleting a task should be restricted to an elevated role, such as a department manager. Caseworkers would progress tasks to `DONE` rather than delete them.
- **Why not now:** There are no users or roles yet (decision 1).
- **Ready for it:** Delete is a single, separate endpoint (`DELETE /api/v1/tasks/:id`), so a role check can be added in one place. Deletions are already recorded in the audit trail (decision 24), so nothing is lost even before permissions exist.

### 26. Error summary keeps GOV.UK autofocus

- **Decision:** On a validation error, focus moves to the GOV.UK error summary at the top of the page. `disableAutoFocus` is not used.
- **Why:** The GOV.UK Design System requires focus to move to the error summary. Screen reader and keyboard users hear "There is a problem" and every error first, and each summary link jumps straight to its field.
- **Detail:** Forms are server-rendered, so the page reloads at the top regardless. Removing autofocus would only stop the errors being announced.
- **Considered:** Keeping focus on the field being edited. Rejected because it goes against GOV.UK accessibility guidance.

### 27. No disabled submit button

- **Decision:** The "Create task" button stays active while errors are showing. Users fix the fields and resubmit.
- **Why:** GOV.UK advises against disabled buttons: poor contrast, they confuse some users, and they don't say what is wrong. Specific error messages tell users how to fix the problem.
- **Detail:** Disabling the button would need client-side validation, which duplicates the server's rules and breaks the form without JavaScript. GOV.UK says to add client-side validation only where there is a user need for it.
- **Considered:** Greying out the button until errors are fixed. Rejected for the reasons above.

### 28. Frontend calls the API server-side

- **Decision:** The Express frontend calls the API with axios from its own server. The browser only ever talks to the frontend.
- **Why:** No CORS configuration needed, the API is not exposed to the public, and pages work without JavaScript.
- **Detail:** The API location is configured with `API_URL` (default `http://localhost:4000`). Requests time out after 5 seconds. If the API is unreachable, users see the GOV.UK "Sorry, there is a problem with the service" page.

### 29. Due date entered as date plus time, in UK time

- **Decision:** GOV.UK date input extended with hour and minute boxes, labelled "Use the 24-hour clock, UK time". Converted from Europe/London to UTC before it is sent to the API.
- **Why:** The time matters for caseworker deadlines and audit logs. Without conversion, every due date set during British Summer Time would be stored an hour out.
- **Detail:** Conversion uses the built-in `Intl` API with a two-pass offset calculation, so it handles the days the clocks change. No date library was added. Covered by unit tests for GMT, BST and the clock change.

### 30. Date checked locally, business rules checked by the API

- **Decision:** The frontend checks that the date boxes form a real date and time. The API remains the only place that enforces "must be in the future" and every other rule.
- **Why:** An unreal date (31 February) cannot be turned into a timestamp to send. Keeping all business rules in the API means one source of truth.
- **Detail:** If the date is invalid, the form is still sent without it, so the user sees every error at once. The local date error replaces the API's.

### 31. API error codes mapped to GOV.UK wording

- **Decision:** One table maps each field and code to a GOV.UK-style message ("Enter a title", "Select a status").
- **Why:** Users never see technical messages, and the wording follows GOV.UK error message guidance.
- **Detail:** An unexpected code shows the generic error page rather than a half-built error list (fail closed).

### 32. Post/Redirect/Get with success banners

- **Decision:** Every successful form redirects. A GOV.UK success notification banner is driven by an allowlisted query key (`?success=created`).
- **Why:** Refreshing the page cannot resubmit a form. The URL cannot be used to inject arbitrary banner text.
- **Considered:** Toast pop-ups. Rejected as not a GOV.UK pattern and inaccessible.

### 33. Deletion uses a confirmation page, not a modal

- **Decision:** "Delete task" opens a confirmation page that names the task and warns it cannot be undone. The delete itself is a POST.
- **Why:** This is the GOV.UK pattern. It works without JavaScript, and nothing destructive happens on a GET.

### 34. Fixes to the HMCTS frontend starter

- **Error handler never ran:** Express only treats middleware with four parameters as an error handler. The starter's had three, so errors were never handled. Fixed, and it no longer shows error details to users.
- **CI never ran:** the workflows targeted `master` and the repo uses `main`. The starter's `yarn test` script exits successfully when `CI=true`, so CI calls the test scripts directly.
- **Node 22 crash:** Yarn PnP's loader broke `ts-node` on Node 22. Switched Yarn to the `node-modules` linker.
- **Header:** `X-Powered-By` disabled, matching the API.
