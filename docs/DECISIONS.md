# Decisions log: HMCTS caseworker task manager

Running log of design decisions and reasons. Feeds the README's "Decisions and trade-offs" section and interview prep.

## Scope

| Area      | Brief requires                                           | Decision                                          |
| --------- | -------------------------------------------------------- | ------------------------------------------------- |
| Create    | title, description (optional), status, due date/time     | As specified                                      |
| Read      | one task by ID, all tasks                                | `GET /tasks/:id`, `GET /tasks` (list, not search) |
| Update    | status only                                              | `PATCH /tasks/:id/status`                         |
| Delete    | one task                                                 | `DELETE /tasks/:id`                               |
| Frontend  | full CRUD, user-friendly                                 | GOV.UK Design System via HMCTS frontend starter   |
| Technical | tests, database, validation and errors, API docs, README | All in scope                                      |

## Decisions

### 1. No users or authentication

- **Decision:** Not built. The brief has no users or permissions.
- **Why:** Out of scope; adding it is over-engineering for a technical test.
- **Next step (README):** In production, tasks would be scoped to the authenticated caseworker via HMCTS identity and access management.

### 2. Statuses

- **Decision:** `TODO`, `IN_PROGRESS`, `ON_HOLD`, `DONE`.
- **Why:** Small, defensible set. `ON_HOLD` reflects real casework, where tasks stall waiting on parties, evidence or the judiciary.

### 3. Overdue is derived, not stored

- **Decision:** API returns `isOverdue` = `dueAt < now` AND `status != DONE`. UI shows a red GOV.UK tag.
- **Why:** A stored flag goes stale as time passes. Deriving it keeps data consistent with no background jobs.

### 4. Due date cannot be in the past on create

- **Decision:** `POST /tasks` rejects a past `dueAt` with 400 and a clear message.
- **Why:** Prevents data entry errors on new work.
- **Allowed:** Status updates on overdue tasks, so they can be progressed and closed.
- **Next step (README):** Historic or backdated tasks would be loaded through an admin-only bulk import with audit logging, not the standard create endpoint.

### 5. Time zones

- **Decision:** Store `dueAt` in UTC. Display in Europe/London.
- **Why:** Avoids tasks shifting by an hour across clock changes.

### 6. Sorting and filtering on `GET /tasks`

- **Decision:** User-controlled sorting and an optional status filter.
  - `?sort=dueAt|status|createdAt` (default `dueAt`)
  - `?order=asc|desc` (default `asc`)
  - `?status=TODO|IN_PROGRESS|ON_HOLD|DONE` (optional)
- **Why:** Due date matters most, but caseworkers also navigate by status and by when work arrived.
- **Detail:** Status sorts by workflow order (TODO, IN_PROGRESS, ON_HOLD, DONE), not alphabetically.
- **Detail:** Sort and filter values are validated against an allowlist; anything else returns 400. Prevents injection via sort fields and gives clear errors.
- **Next step (README):** Pagination for large caseloads.

### 7. Stack

- **Decision:** Node.js + TypeScript, Express 5, Postgres (Docker Compose), Knex for migrations and queries, Jest + Supertest, Zod for validation, OpenAPI for docs. Frontend: HMCTS frontend starter with the GOV.UK Design System.
- **Why:** Node.js and Postgres are on HMCTS's core stack; TypeScript adds type safety; GOV.UK Design System matches how HMCTS builds public services.
- **Detail:** `createApp()` is separate from `server.ts` so tests run against the app without opening a network port.

### 8. Task IDs are UUIDs

- **Decision:** `id` is a UUID generated by Postgres (`gen_random_uuid()`).
- **Why:** Sequential numbers are guessable (`/tasks/1`, `/tasks/2`) and reveal task volumes. UUIDs prevent ID enumeration, which matters for a justice system even before authentication is added, and stay unique across systems for future imports.
- **Trade-off:** Less readable than numbers. Ordering is handled by `createdAt` instead.

### 9. Database schema and migrations

- **Decision:** Schema managed through Knex migrations, with an `up` and a `down` for every change.
- **Why:** Versioned, repeatable and reversible changes instead of manual SQL. Knex also builds parameterised queries, which protects against SQL injection.
- **Schema details:**
  - `title` limited to 200 characters and required; `description` optional.
  - `status` restricted by a database check constraint to `TODO`, `IN_PROGRESS`, `ON_HOLD`, `DONE`, so invalid values are rejected even if they bypass the API.
  - `due_at`, `created_at` and `updated_at` stored as timestamps with time zone (UTC).
  - Indexes on `due_at` and `status`, because the list endpoint sorts and filters on them.
- **Trade-off:** A check constraint rather than a Postgres enum type, because it is simpler to change if statuses are added later.

### 10. Error response format (API)

- **Decision:** All errors return `{ error: { code, message, details? } }`. Field errors return `details` with one entry per field: `{ field, code, message }`.
- **Audience:** API messages are for developers. The frontend maps codes to user-facing text (see decision 11).

| Status | Code                | When                                                               |
| ------ | ------------------- | ------------------------------------------------------------------ |
| 400    | `MALFORMED_JSON`    | Request body is not valid JSON                                     |
| 404    | `NOT_FOUND`         | No task with that ID, including IDs that are not valid UUIDs       |
| 404    | `ROUTE_NOT_FOUND`   | URL or method does not exist                                       |
| 413    | `PAYLOAD_TOO_LARGE` | Body exceeds size limit                                            |
| 422    | `VALIDATION_ERROR`  | Well-formed request with invalid values (includes `details`)       |
| 500    | `INTERNAL_ERROR`    | Unexpected error; generic message, details logged server-side only |

- **Field codes:** `REQUIRED`, `TOO_LONG`, `INVALID_FORMAT`, `INVALID_VALUE`, `DATE_IN_PAST`, `UNKNOWN_FIELD`.
- **Why 422:** Separates "the request is broken" (400) from "the request is valid JSON but breaks the rules" (422).
- **Why 404 for invalid IDs:** A malformed ID can never match a task, so the answer is the same as any missing task. Reveals nothing about ID format and keeps clients simple. Invalid UUIDs are caught before querying so they never cause a database error.
- **Why reject unknown fields:** Catches client typos instead of silently ignoring them, and keeps `PATCH` limited to `status`.
- **Delete of a missing task:** 404, consistent with other endpoints.
- **Status on create:** Required. The database default (`TODO`) remains as a safety net only.
- **Alternative considered:** RFC 9457 Problem Details. A recognised standard, but heavier than needed for this scope.
- **One error per field:** If a field fails several rules, only the first is returned, so users never see duplicate messages for one input.
- **Missing vs invalid:** A field that was not sent returns `REQUIRED`; a field that was sent but is wrong returns the specific code.

### 11. User-facing error messages (frontend)

- **Decision:** The frontend never shows API messages directly. It maps error codes to plain-English text following the GOV.UK Design System error message guidance, shown in an error summary at the top of the page and next to each field.

| Field / code                                            | User sees                                                    |
| ------------------------------------------------------- | ------------------------------------------------------------ |
| title / `REQUIRED`                                      | Enter a title                                                |
| title / `TOO_LONG`                                      | Title must be 200 characters or fewer                        |
| status / `REQUIRED`                                     | Select a status                                              |
| status / `INVALID_VALUE`                                | Select a status from the list                                |
| dueAt / `REQUIRED`                                      | Enter a due date                                             |
| dueAt / `INVALID_FORMAT`                                | Due date must be a real date                                 |
| dueAt / DATE_IN_PAST: “Due date must be in the future”. |
| `NOT_FOUND` (page)                                      | Task not found. It may have been deleted.                    |
| `INTERNAL_ERROR` / network failure                      | Sorry, there is a problem with the service. Try again later. |

- **Why:** Developer messages and user messages have different audiences. Mapping by code keeps wording consistent, lets content change without touching the API, and follows GOV.UK standards caseworkers already know.
- **Not shown to users:** `MALFORMED_JSON`, `ROUTE_NOT_FOUND`, `PAYLOAD_TOO_LARGE`, `UNKNOWN_FIELD`. These indicate a frontend bug; the user sees the generic service error and the detail is logged.

### 12. Description length

- **Decision:** `description` is optional and capped at 2000 characters.
- **Why:** Prevents oversized payloads in a free-text field while leaving room for real case notes.
